## CI/CD via GitHub Actions (aligned to TicTic android-ci.yml pattern)

Since the sandbox lacks Java/Android SDK, all Gradle/Android builds run on GitHub-hosted runners following the TicTic `android-ci.yml` proven pattern:

- `.github/workflows/android-ci.yml` — CI lane on push/PR: traceability (strict), detekt, assemble debug + release APKs, static gates (no internet permission, APK <= 25 MB), lane aggregation (if: always()). 6 jobs, <= 3 runners. Uses `sh gradlew`, `continue-on-error: true` + `tee` on build/test steps, GitHub annotation error surfacing (critical since review sandbox can't download logs), persistent sideload signing key (`signing/onedoc.p12`), Gradle caching, `fetch-depth: 0`, `actions/upload-artifact@v4` with `if: always()`.
- `.github/workflows/onedoc-release.yml` — release lane (workflow_dispatch): assemble release APKs, provenance.json, create GitHub Release with APKs + SHA-256.
- `.github/workflows/pr.yml` — PR fast lane: traceability, lint (banned vocabulary + detekt), static gates, lane aggregation (if: always()). 4 jobs.
- Gradle wrapper: `gradlew`, `gradlew.bat`, `gradle/wrapper/gradle-wrapper.properties` (jar generated in CI via `gradle wrapper`).

CI budget C8 respected: max 3 parallel runners, <= 30 jobs per run. Publisher/report jobs use `if: always()`.
